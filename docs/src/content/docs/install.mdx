Download the package for your platform from the [releases page](https://github.com/timmo001/system-bridge/releases).

Each release ships these assets:

- Arch Linux: `system-bridge-*-x86_64.pkg.tar.zst` (stable releases only)
- Debian / Ubuntu: `system-bridge_<version>_<arch>.deb`
- Fedora / RHEL: `system-bridge-<version>.<arch>.rpm`
- Flatpak: `system-bridge-<version>.flatpak`
- Linux archive: `system-bridge-<version>-linux-x86_64.tar.gz`
- Windows: `system-bridge-<version>-setup.exe`
- Windows archive: `system-bridge-<version>-windows-x86_64.zip`

The archives hold just the executable, for [mise](https://mise.jdx.dev) and manual installs. Prefer a package where there is one, as the archives don't set up a service, shortcuts or dependencies.

:::note
Stable builds are attached to the releases page. Development builds from the latest `dev` branch are also available as workflow artifacts on the [GitHub Actions runs](https://github.com/timmo001/system-bridge/actions), which require a GitHub account to download.
:::

Install the package that matches your distribution's package manager, or use mise or the archive on any distribution.

<Tabs syncKey="distro">
<Tab title="Arch Linux">

Install from the AUR with an AUR helper such as [yay](https://github.com/Jguer/yay).

For the latest stable release, use the [system-bridge](https://aur.archlinux.org/packages/system-bridge) package:

```bash
yay -S system-bridge
```

For the development branch, use the [system-bridge-git](https://aur.archlinux.org/packages/system-bridge-git) package. This builds and installs the application from the latest `dev` branch, which is updated automatically every commit:

```bash
yay -S system-bridge-git
```

Alternatively, install the `.pkg.tar.zst` from the releases page or downloaded workflow asset directly:

```bash
sudo pacman -U system-bridge-*-x86_64.pkg.tar.zst
```

</Tab>
<Tab title="Debian / Ubuntu">

Install the `.deb` asset with `apt` so dependencies are resolved automatically:

```bash
sudo apt install ./system-bridge_<version>_<arch>.deb
```

You can also install it with `dpkg`:

```bash
sudo dpkg -i system-bridge_<version>_<arch>.deb
```

<Tab title="NixOS">

The repository is a Nix flake that builds System Bridge from source on x86_64 Linux, from the latest `dev` branch. Run it without installing:

```bash
nix run github:timmo001/system-bridge -- backend --open-web-client
```

Or add it to your NixOS configuration as a flake input:

```nix
{
  inputs.system-bridge.url = "github:timmo001/system-bridge";

  outputs = { nixpkgs, system-bridge, ... }: {
    nixosConfigurations.<host> = nixpkgs.lib.nixosSystem {
      modules = [
        {
          environment.systemPackages = [
            system-bridge.packages.x86_64-linux.default
          ];
        }
      ];
    };
  };
}
```

`system-bridge-full` is the same package with most of the [optional dependencies](#optional-dependencies) added to its `PATH`: `lm_sensors`, `pciutils`, `pipewire`, `pulseaudio` (for `pactl` and `paplay`, which work with PipeWire's `pipewire-pulse` too), `alsa-utils`, `zenity` and `ddcutil`. Use `system-bridge.packages.x86_64-linux.system-bridge-full` instead of `default` to get them, or add whichever you want to `environment.systemPackages` with the plain package.

The rest come from NixOS options, with either package:

- `nvidia-smi` comes with the NVIDIA driver, from `hardware.nvidia` and `services.xserver.videoDrivers = [ "nvidia" ]`, so it always matches the driver that's running.
- Bluetooth devices need `hardware.bluetooth.enable = true`.
- `ddcutil` needs `hardware.i2c.enable = true`, with your user in the `i2c` group.

If you run System Bridge from `systemd.user.services` in your configuration, NixOS gives the service a minimal `PATH`, so it won't find tools from `environment.systemPackages`. Use `system-bridge-full`, or list the tools in the service's `path`.

<Tab title="mise">

[mise](https://mise.jdx.dev) installs the Linux archive from the latest release:

```bash
mise use -g github:timmo001/system-bridge
```

Pin a version with `github:timmo001/system-bridge@<version>`. mise checks the download against the release's [GitHub attestation](https://docs.github.com/actions/security-for-github-actions/using-artifact-attestations).

The executable needs `libx11`, `libxtst`, `libxkbcommon` and `libxkbcommon-x11` (`libx11-6`, `libxtst6`, `libxkbcommon0` and `libxkbcommon-x11-0` on Debian / Ubuntu), even without a desktop. Nothing starts it for you: run `system-bridge backend`, or add your own service or autostart entry. See [Running](/running).

gh release download -R timmo001/system-bridge -p '*-linux-x86_64.tar.gz'

The executable needs the same libraries as with mise, and nothing starts it for you. See [Running](/running).

## Updating

On Linux, System Bridge restarts itself within a minute of a package update replacing it, so the new version runs without you restarting it. Flatpak keeps running the version it started with, so restart System Bridge after updating it there.

The same goes for replacing the Linux executable from an archive by hand. mise installs each version to its own folder instead, so restart System Bridge after `mise upgrade`, and after updating from the Windows archive.

## Optional dependencies

System Bridge reads most hardware metrics directly from the kernel, so these tools aren't required. On Linux, installing them improves detection on some systems:

| Package | Tool | What it adds |
| --- | --- | --- |
| `lm_sensors` (Arch, Fedora), `lm-sensors` (Debian / Ubuntu) | `sensors` | The full set of temperature and fan sensors on some boards. Run `sudo sensors-detect` once to load the relevant modules. |
| `nvidia-utils` | `nvidia-smi` | NVIDIA GPU metrics. Intel and AMD GPUs use the kernel `drm`/`hwmon` interfaces and need nothing extra. |
| `pciutils` | `lspci` | Friendly GPU model names. GPUs are still detected without it, but fall back to a generic name. |
| `pipewire` (Arch), `pipewire-bin` (Debian / Ubuntu), `pipewire-utils` (Fedora) | `pw-dump` | Names the apps using the microphone or camera. Without it, microphone usage falls back to ALSA, which names the sound server instead of the app. |
| `zenity` | `zenity` | The confirmation before **Quit** or **Hide system tray**. Without it, those actions can't be confirmed, so they don't run. |
| `libpulse` (Arch), `pulseaudio-utils` (Debian / Ubuntu, Fedora) | `pactl`, `paplay` | Audio devices and [audio controls](/features/remote-control/#audio), and notification sounds. Needs PulseAudio 16 or later, or PipeWire with `pipewire-pulse`. |
| `alsa-utils` | `aplay` | Notification sounds when `paplay` isn't installed. |
| `bluez` | `bluetoothd` | Bluetooth devices and [Bluetooth controls](/features/remote-control/#bluetooth). |
| `ddcutil` | `ddcutil` | Brightness and power for [external monitors](/features/remote-control/#displays) over DDC/CI. Needs access to `/dev/i2c-*`, usually by being in the `i2c` group. |

The `.deb` and `.rpm` packages recommend `pciutils`, PipeWire, `zenity` and `pulseaudio-utils`, so `apt` and `dnf` install them by default. The Arch package lists all of these as optional dependencies, which `pacman` shows but doesn't install.

The [command prefabs](/features/commands/#prefab-commands) run tools for the desktop you're on, such as `wl-clipboard` for the clipboard or `grim` for screenshots. A prefab that can't run says which tools it looks for. [Setting the clipboard](/features/remote-control/#clipboard) uses the same clipboard tools.

On Windows, the waiting package update count needs [winget](https://learn.microsoft.com/windows/package-manager/winget/), which Windows 11 includes. Nothing else is needed.

## Power readings on Linux

CPU power, integrated Intel GPU power and, on laptops, system power come from the kernel's RAPL energy counters. Since [CVE-2020-8694](https://nvd.nist.gov/vuln/detail/CVE-2020-8694) the kernel lets only root read them, so the Arch, `.deb` and `.rpm` packages install a udev rule, `60-system-bridge-rapl.rules`, that makes them readable by every local user.

:::warning
Readable counters let local programs measure power use, which CVE-2020-8694 showed can leak data from the CPU, mostly from SGX enclaves. If that matters on your system, delete or override the rule with an empty `/etc/udev/rules.d/60-system-bridge-rapl.rules`. Those readings then stay empty; on battery, system power still comes from the battery.
:::

mise, the archive and Flatpak can't install the rule. Add it yourself, then apply it without a reboot:

```ini title="/etc/udev/rules.d/60-system-bridge-rapl.rules"
SUBSYSTEM=="powercap", KERNEL=="intel-rapl:*|intel-rapl-mmio:*", ACTION=="add|change", RUN+="/bin/chmod a+r /sys%p/energy_uj"
```

```bash
sudo udevadm control --reload
sudo udevadm trigger --subsystem-match=powercap --action=change
```

On NixOS, add the package to `services.udev.packages` as well.
