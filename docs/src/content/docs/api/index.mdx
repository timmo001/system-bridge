System Bridge exposes your system over a local API. There are three ways to interact with it: an HTTP API for simple request/response calls, a WebSocket API for live data and control, and an MCP server for agents.

The [WebSocket API](/api/websocket/) is the primary interface and covers most operations: live data, input, media and power control, notifications, settings, and commands. Reach for HTTP only when you want a quick one-off read of status or a module's current data.

## Base URL

By default the backend listens on port `9170`, so the base URL is:

```text
http://{host}:9170
```

Replace `{host}` with the hostname or IP address of the machine running System Bridge. The port can be changed with the `SYSTEM_BRIDGE_PORT` environment variable.

## Authentication

Most endpoints need a key. Each client has its own, so you can see which clients connect and remove one without touching the others. A key looks like `system-bridge_client_` followed by 49 letters and digits, and it's only shown once, when it's made. System Bridge keeps a hash of it, never the key.

A client gets its key by:

- [Pairing](/api/pairing), for the Android app.
- Being made by hand, under **Settings > Devices** in the web client, or on the computer with:

  ```bash
  system-bridge client key create "My script"
  ```

On first start, System Bridge also makes an owner key and writes it to the `owner-key` file in the [settings directory](/running/#file-locations), readable only by your user. The CLI signs in with it. See [keys in the CLI](/using/cli/#keys).

How you send the key depends on the protocol:

- **HTTP**: send `Authorization: Bearer {key}`.
- **WebSocket**: send `{"type": "auth", "key": "{key}"}` as the first message. See [signing in](/api/websocket/#signing-in).
- **MCP**: send `Authorization: Bearer {key}`.
- **Media files**: ask for a [signed URL](/api/media-file-data), which holds no key.

The `GET /api` and `GET /api/health` endpoints do not need a key.

### Moving from the API token

Before keys, every client used one shared API token. A client that has it can [trade it for its own key](/api/keys#exchange-the-api-token), once. Until the token is removed in a later release, it still works where it did: in the `X-API-Token` or `token` header, as a Bearer, in each WebSocket message's `token` field, and in the `token` query parameter of the MCP and media file endpoints.

### When to use which

| Protocol | Best for |
| --- | --- |
| WebSocket | Most operations: live updates, control actions (media, power, notifications, input), settings, and commands. |
| HTTP | Simple one-off reads: health checks and fetching a module's current data. |
| MCP | Letting agents query data and trigger actions. |
